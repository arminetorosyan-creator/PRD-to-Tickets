# Definition of Done — Verification Process

Every ticket generated by the `prd-to-tickets` skill carries the same
7-item Definition of Done (DoD). This page defines **who** verifies each
item, **how**, and **at what point** in the workflow — so the checklist on
a ticket isn't just a box to tick, but maps to an actual gate someone owns.

It's a default process, not a mandate: adapt roles/stages to your team's
actual tools (Jira workflow states, CI system, environments) and override
per-project where needed — e.g. regulated tickets (sanctions decisioning,
auto-hold configuration, suppression rules) should route sign-off through
Compliance/MLRO in addition to the Product Owner, per the Four-Eyes
principle those PRDs already require.

## The 7 items

| # | DoD item | Verified by | How | When (workflow gate) |
|---|---|---|---|---|
| 1 | Acceptance criteria met and verified | QA/Tester (developer if no dedicated QA) | Execute each Given/When/Then manually, or run the automated test mapped to it | End of "In Progress" → before moving into Review |
| 2 | Code reviewed and approved | A peer engineer, not the author. For compliance-critical stories (Four-Eyes items), a second, more senior reviewer | Pull request review against a checklist: logic, security, standards | Before merge to the main/integration branch |
| 3 | Automated tests (unit/integration) written and passing | The implementing developer | Tests run in CI; must be green | CI gate — same stage as code review, blocks merge if failing |
| 4 | No regression introduced in existing functionality | QA, with CI running the regression suite | Automated regression suite plus smoke-testing of adjacent features | After merge, before deploy to staging/UAT |
| 5 | Relevant documentation updated | Developer (technical docs: API, config, data model) + BA/PO (user-facing docs, runbooks) | Update README/wiki/API docs; reviewed in the same PR | Before the ticket is marked Done |
| 6 | Deployed to staging/UAT and verified | DevOps/release engineer deploys; QA or PO verifies | CI/CD deploy to staging/UAT, then scripted or exploratory verification against the AC | After regression passes, before sign-off |
| 7 | Product Owner sign-off obtained | Product Owner (+ Compliance/MLRO co-sign for regulated tickets) | Review in UAT against AC + DoD; approval recorded on the ticket | Final step — before the ticket is eligible for release |

## How this maps to a Jira workflow

```
To Do → In Progress → Code Review → QA / Regression → UAT → Done
          │               │              │              │      │
        item 1          items          item 4         item 6  item 7
                        2 & 3
```

Each DoD line gates one transition rather than all seven being checked in
a single pass at the end. A ticket shouldn't move to the next column until
the item(s) gating that transition are satisfied.

## Where this shows up in the deliverables

Every ticket's "Definition of Done" section in the generated `.docx`
drafts includes the **Verified by** and **When** for each item inline, so
a ticket is self-contained once imported into Jira — a reviewer doesn't
need to come back to this page to know who's expected to check what.
